# NDLOCR-Lite 採用可否の調査

調査日: 2026-10-21
対象: NDLOCR-Lite（国立国会図書館 NDLラボ、2026-02-24 公開。https://lab.ndl.go.jp/news/2025/2026-02-24/ ）
手段: 公式リポジトリ・README・Issue・リリースノートの確認 ＋ 手元の `input/1.png`〜`10.png` での実機比較（M4 / CPU / Python 3.13）

---

## 結論

**採用は適切。GLM-OCR に代わるメイン OCR の第一候補。** 本プロジェクトの絶対条件（完全ローカル・NVIDIA GPU なし）を満たし、
手元の資料 10 枚で GLM-OCR より速く・正確で、GLM-OCR の最大の問題（反復ループとページ丸ごとの失敗）が起きなかった。
ただし「同じ字の連続」に弱いという既知の弱点が手元でも出たので、後処理で受ける必要がある。

2026-02-08 の調査（`戦前日本語OCR調査レポート.md`）で「NDLOCR ver.2 は NVIDIA GPU 前提なので使えない」とした判断は今も正しい。
NDLOCR-Lite はその後（2026-02-24）に公開された CPU 版で、別物として扱う。

## 1. 概要

| 項目 | 内容 |
|---|---|
| 開発元 | 国立国会図書館（NDLラボ） |
| 最新安定版 | v1.3.1（2026-09-07）。偶数マイナーのプレビュー版（1.2.0、1.3.0）は不安定な場合があると NDL が明言（Issue #43） |
| ライセンス | CC BY 4.0（出典表示）。同梱のレイアウトモデルは DINOv3 由来で、DINOv3 ライセンスの遵守も必要 |
| 構成 | レイアウト認識 DEIMv2 → 文字列認識 PARSeq → 読み順整序（NDLOCR と同じモジュール）。ONNX Runtime |
| 動作環境 | CPU のみで動作。Docker 不要。README の動作確認環境に Mac（Apple M4, macOS Sequoia）。Python 3.10 以上（3.13 可、3.14 は macOS の onnxruntime に wheel がなく不可: Issue #38） |
| Apple Silicon の GPU | 非対応（Issue #54。onnxruntime が MPS の実行プロバイダを持たないため）。CPU でも十分速い |
| モデル | 同梱 ONNX 4 ファイル・約 150MB。実行時のダウンロードなし |
| 外部送信 | `src` と GUI のコードに通信・テレメトリの処理なし（grep で確認）。依存ライブラリ内部の通信と、パケットを見ての検証は未実施 |
| 出力 | TXT / JSON（行ごとの座標・text・confidence・isVertical）/ XML（ORDER＝読み順）/ 透明テキスト PDF |
| Python API | 公式の安定 API なし。CLI（`--sourcedir` でモデルを 1 回だけロード）を subprocess で呼び、JSON を読むのが現実的 |

公表精度（`evaluation_jptype.csv`、NDLOCR ver.2.1 と同じ評価データ）: 全体の F 値中央値 0.9718（ver.2.1 は 0.9727）。
1900〜1930 年代の図書 0.967〜0.979、明治初期（1870〜90 年代）は 0.88〜0.96 とやや低い。手書きは CER 0.27 前後で実験的な水準。
くずし字・古典籍は対象外（NDL古典籍OCR を使う）。

## 2. 実機比較（2026-10-21、`input/1.png`〜`10.png`、前処理なしの元画像）

| 項目 | GLM-OCR（G12 対応後） | NDLOCR-Lite（master, d001dad） |
|---|---|---|
| 10 枚の所要時間 | 約 2 分（1 枚 13.5〜14.9 秒） | **9 秒**（起動・モデル読み込み込み。認識は 1 枚約 0.7 秒） |
| 失敗ページ | 1 枚（5 枚目は毎回反復検知で全損） | **0 枚** |
| 反復ループ | 全ページ（切り落としで対処） | なし |
| 5 枚目 | 0 字 | 397 字（画像と照合して誤り 4 か所） |
| 8 枚目 | 138 字（途中から反復） | 279 字（ページ末尾まで） |
| その他のページ | 179〜396 字 | ほぼ同じ字数（±5 字前後） |
| 行の情報 | なし（本文のみ） | 行ごとの座標・信頼度・読み順 |

5 枚目を画像と 1 字ずつ照合した結果: 422 字（空白込み）中の誤りは、似た形の漢字の取り違え 1、同じ字の重複 1、鉤括弧の脱落 1、
カタカナ「ヘ」がひらがな「へ」になる 1 の計 4 か所。旧字体は旧字体のまま、和歌のひらがなも正しく出た。

GLM-OCR が繰り返していた系統的な誤読（カタカナ「ニ」→漢数字「二」、「ヲ」→「チ」、旧字体→新字体、似た字の取り違え）は、
8 枚目の冒頭を比べた範囲では NDLOCR-Lite では起きていない。

## 3. 懸念点と対処

- **同じ字の連続に弱い**（公式 Issue #43）: 手元でも「同じ字が 2 回続く」誤り（重複）がページ 5 で 1 か所（画像で確認）、ページ 9 で 2 か所（画像では未確認だが文脈上重複とみられる）出た。
  逆に正しい連続（「々」を使わない重ね字など）もありうるので、機械的に消すのは危険。差分表示（`prewar diff`）で人が確認する運用か、
  信頼度（JSON の `confidence`、手元では最低 0.60〜0.95）が低い行だけ警告する形が現実的
- **縦書きの行全体が崩れる例**（Issue #56）: 手元の 10 枚では見ていない。NDL は次期モデルで確認するとしている
- **空白と改行**: 句読点の後に半角空白が入り、行（縦書きの 1 列）ごとに改行される。既存の正規化に空白除去と行の連結が要る
  （行単位の出力は B3 ページ境界の連結にはむしろ好都合）
- **依存の衝突**: `requirements.txt` は numpy・onnxruntime を固定し、GUI 用の flet も含む。プロジェクトの環境に直接入れず、
  `uv tool install` などで隔離して CLI を呼ぶのが安全
- **Python API が非公式**: 内部関数を import すると版上げで壊れうる。CLI ＋ JSON の境界で使う
- **明治初期の精度**: 公表値で 0.88〜0.96。手元の資料（昭和初期の活字と推定）では問題ないが、明治初期の資料では要確認

## 4. 次の一手（提案）

OpenSpec の変更として「OCR エンジンを NDLOCR-Lite に切り替える（GLM-OCR は選択肢として残す）」を起票する。論点:

1. 導入方法（`uv tool install` で隔離 / git submodule / 版の固定 v1.3.1）と、`prewar check` での導入確認
2. `ocr_client` の差し替え口（`[ocr] engine = "ndlocr-lite" | "glm-ocr"`）と、JSON から本文・信頼度への変換
3. 空白除去と列の連結（正規化の前段）、低信頼度行の警告、`meta.json` への記録
4. 画像前処理（A1）を NDLOCR-Lite に通すか（今回は元画像で十分読めた）
5. G12 の反復対策は GLM-OCR を選んだときだけ効く形で残す
