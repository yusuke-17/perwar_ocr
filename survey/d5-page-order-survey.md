## 1. 結論（先に要点）

- **`plan/improvement-ideas.md` の D5 記述は事実**。並べ替えは3箇所とも文字列順で、
  実物の `input/1.png`〜`32.png` では **32枚中31枚の位置がずれる**（正しい位置に残るのは `1.png` だけ）。
  エラーも警告も出ず、そのまま1文書に結合されて口語体に変換される。
- **自然順ソートは外部依存なし・15行程度で書け、確認した名前の形式はほぼ直る**。
  0埋めなし連番、日本語スクショ名、同じ秒の ` (2)`、全角数字、`p1000` 超え、拡張子混在はすべて期待順になった。
- **自然順でも直らない形式が3つある**。英語の AM/PM 表記のスクショ名、漢数字（`第十頁`）、
  iPhone の `IMG_9999` → `IMG_0001` の巻き戻り。名前だけでは原理的に順序が決まらない。
- **撮影日時（mtime）は「既定の並べ順」には向かないが「食い違いの検知」には使える**。
  `cp` でコピーすると日時が変わるため既定にはできない。一方、実物32枚では mtime 順と番号順が一致しており、
  「名前順と日時順が食い違ったら警告する」ようにすれば、直らない3形式も黙って通さずに済む。
- **既存の記録への被害はない**。`library/` は現在0件。
- **調査で見つかった周辺の問題が4件ある**（6 章）。特に「`.tif` / `.webp` がフォルダ処理で黙って無視される」は
  D5 と同じ「ページが静かに欠ける」種類なので、同じ変更に含めるか判断が要る。

## 4. 自然順ソートの実装方式

### 4-1. 自作か、ライブラリか

| | 自作（標準ライブラリのみ） | `natsort` |
|---|---|---|
| 規模 | キー関数1つ、15行程度 | 依存1つ追加（必須の追加依存はなし） |
| 保守状況 | — | 最新 8.4.0 は2023年のリリース。対応表記は Python 3.7〜3.11 で、3.13 での動作は未確認 |
| Finder と同じ並び | 完全一致はしない | `os_sorted` があるが、macOS では PyICU（別途導入）なしだと正しくならない可能性がある |
| 細かい規則の調整 | 自由（拡張子の扱い、同値の決め方など） | オプションの範囲内 |

**推奨は自作**。必要な規則が少なく、G8 で依存を減らした直後でもある。置き場は `utils/`（PJ固有モジュール）。

### 4-2. 候補実装（実験に使ったもの）

```python
_DIGITS = re.compile(r"(\d+)")

def natural_key(path: Path):
    stem = unicodedata.normalize("NFKC", path.stem).casefold()
    parts = _DIGITS.split(stem)   # 偶数番目=文字、奇数番目=数字 が必ず交互に並ぶ
    key = tuple(
        (1, int(p), len(p)) if i % 2 else (0, p, 0) for i, p in enumerate(parts)
    )
    return (key, path.suffix.lower(), path.name)
```

### 4-3. 実装時の落とし穴（実験で確認済み）

| 落とし穴 | 内容 | 対処 |
|---|---|---|
| 拡張子を含めて比べる | `X.png` と `X (2).png` で `(2)` が先に来る（空白が `.` より前のため） | **拡張子を除いた名前（stem）で比べる** |
| 数字の判定に `isdigit()` を使う | `'²'.isdigit()` は真だが `int('²')` は ValueError | 正規表現 `\d+` で分け、位置（奇数番目）で数字と判断する |
| 数字と文字の比較 | 型が混ざると TypeError | `re.split` の結果は必ず「文字・数字・文字…」の交互になる。念のため種別を先頭に持つ組にする |
| 全角数字 | `\d` は全角数字にも一致し、`int('１０')` は 10 になる | そのままで動く |
| 数値として同じ名前 | `1.png` と `01.png`、`１０` と `10` は数値が同じ | 桁数と元の名前で順序を一意に決める（実行のたびに順序が変わらないようにする） |
| 大文字小文字 | 文字列順では大文字が全部先（`P1, P3, p2`） | `casefold()` でそろえる |
| 濁点の表し方の違い | macOS は「ガ」を1文字（NFC）でも「カ＋濁点」（NFD）でも保存でき、両者は別の文字列として比較される | `unicodedata.normalize` でそろえる。NFKC なら AM/PM 前の特殊な空白（U+202F）も通常の空白になる |

### 4-4. 自然順で直らないもの

- **英語の AM/PM 表記**: AM/PM が時刻の後ろに付くため、数字だけ見ると午後1時が午前9時より前になる。
- **漢数字**: `第十頁` などは数字として扱われない。
- **iPhone の連番の巻き戻り**: `IMG_9999` の次は `IMG_0001` に戻る。
- **順不同に名前を付け直した場合**など、名前がページ順を表していないもの全般。

これらは名前の規則を増やして追いかけるより、5 章の「食い違いの検知」と「並び順の確認」で受け止めるほうが確実。

## 5. 撮影日時による並べ替え

### 5-1. 日時情報の信頼性

| 情報 | 取得 | 信頼性 |
|---|---|---|
| mtime（更新日時） | `stat().st_mtime_ns` | `cp` でコピーすると新しい日時になる。`cp -p`・`ditto`・`unzip` では保たれる（サブエージェントが実測）。Finder コピー、AirDrop、ブラウザのダウンロード、iCloud Drive は未確認 |
| birthtime（作成日時） | macOS では `st_birthtime`（秒の小数）。`st_birthtime_ns` は Windows 専用で、macOS では AttributeError（実測）。Linux には属性自体がない | `cp` で新しくなる |
| EXIF の撮影日時 | Pillow を G8 で削除済み。OpenCV は EXIF を読めない | PNG のスクショには通常入っていない（未確認）。今回は対象外が妥当 |

- 実物 `input/1.png`〜`32.png` は、mtime 順・birthtime 順ともに番号順と完全に一致した（約10秒間隔で単調増加）。
- 同じ秒に複数枚できた場合に備え、秒未満まで持つ `st_mtime_ns` を使い、同値なら自然順で決める。

### 5-2. macOS スクリーンショット名（Web 調査の結果）

- 24時間表示の英語環境では時が0埋めされる例（`Screenshot 2024-11-18 at 08.48.15.png`）、
  12時間表示では0埋めされない例（`… at 5.07.05 PM.png`）が確認できた。
- macOS 14（Sonoma）以降、AM/PM の前の空白は U+202F（幅の狭い改行しない空白）になっている。
- **日本語環境の実際の名前、午前/午後の位置、同じ秒の連写のサフィックス（` (2)` か ` 2` か）は一次情報で確認できなかった**。
  この Mac（`ja_JP`、24時間表示が既定）の時刻表記は `9:05:03` で時が0埋めされないため、
  スクショ名も `9.05.03` になると推測されるが、実ファイルでは未確認。
- どちらの場合でも自然順なら正しく並ぶ（3 章）。確認が要るのは12時間表示にしている場合だけ。

### 5-3. 使い方の案

| 案 | 内容 | 評価 |
|---|---|---|
| A. 既定を撮影日時順にする | — | ✗ コピー経路で壊れる。`shoot` の `pNNN` は名前のほうが確実 |
| B. 並べ方の選択肢に加える | `--order name\|mtime`、対話メニューでも選べるようにする | ○ 名前が当てにならないとき（AM/PM、巻き戻り）の逃げ道になる |
| C. 食い違いの検知に使う | 自然順と mtime 順が違ったら警告し、両方の順を見せる | ◎ 小コストで「静かに壊れる」を「見える」に変えられる |

C は誤警告の可能性がある（コピーで日時が全部同じ・逆順になった場合）。
警告にとどめて処理は止めない、対話時だけ確認を挟む、といった扱いが要る。

## 7. 提案スコープ案（`/opsx:propose` の叩き台）

### 段階の切り方

| 段階 | 内容 | 規模 |
|---|---|---|
| **① 自然順ソート** | キー関数を `utils/` に追加し、2-1 の5箇所を置き換える（`screen_capture.py:150` は `sorted()` を外すだけでもよい）。仕様 `spec.md:121` を「数字部分を数値として比べる順」に改定。コメント・docstring・README の記述を直す | 小 |
| **② 並び順の表示と食い違いの警告** | 処理前に番号付きの一覧で並び順を表示。自然順と mtime 順が違えば警告。対話時は「このまま進む / 撮影日時順にする / やめる」を選べるようにする | 小〜中 |
| **③ 並べ方の指定** | `--order name\|mtime` と `config.toml` の `[batch] order`（既定 `name`） | 小 |
| ④ 手動の入れ替え | 番号入力などで順序を直す。`questionary` に並べ替え機能はないので自前の画面が要る | 中 |
| ⑤ 元ファイル名の記録 | meta.json に元の名前を残す | 小（スキーマの判断が要る） |

**推奨は ①〜③ を1つの変更にまとめること**。① だけでも実物の崩れは直るが、4-4 の直らない形式が黙って通る状態が残る。
②③ は同じ関数まわりの変更で、テストの仕込みも共通。④⑤ は使ってみてから判断でよい。
急ぐなら `plan/improvement-ideas.md` のとおり ① だけ先に入れても害はない。

### テストの観点（① の場合）

- キー関数: 3 章の表の各形式（✓ になるもの）と、4-3 の落とし穴（`²`、全角、`01` と `1`、NFC/NFD、大文字小文字）
- `load_folder_images`: `1.png`〜`12.png` を置いたフォルダで順序を確認（既存テストは `pNNN` のみ）
- `process_folder` を通した結合順: 結合後のテキストがページ番号順になること
- 旧形式の出力名: `1.png`〜`12.png` で `1-12_modern.txt` になること
- `pNNN` 形式の既存テストが変わらず通ること（0埋めの名前は自然順でも同じ結果）

### 決めておきたい論点

1. **スコープ**: ① だけ先に入れるか、①〜③ をまとめるか。
2. **6 章の 1〜3 を含めるか**: 列挙の関数を1つにまとめるなら同時に直すのが自然。別の変更に分けることもできる。
3. **食い違い警告の扱い**: フォルダ指定（非対話）のときは警告表示だけで進めるか、終了コードに反映するか。
4. **`shoot` の扱い**: `pNNN` は名前が確実なので、食い違い警告の対象から外すか。
5. **英語 AM/PM 表記への個別対応**: 名前の規則で直すか、警告と撮影日時順に任せるか（推奨は後者）。
6. **12時間表示のスクショ名の実機確認**: 12時間表示で使う予定があるなら、1枚撮って名前を確かめる。

| 1 | スコープ | ①〜③ を1つの変更にまとめる（④手動の入れ替え・⑤元ファイル名の記録は含めない） |
| 2 | 6 章の 1〜3 | 含める。画像の列挙と並べ替えを1つの関数にまとめる |
