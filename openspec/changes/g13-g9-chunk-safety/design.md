# Design

## Context

動機は proposal.md の Why を参照。ここでは設計を決めるのに必要な現状だけを書く。

- `TextModernizer._chat()` は応答の本文（`response.message.content`）だけを返し、`done_reason` を捨てている。OCR 側（`OllamaOCRClient._call_ollama`）はすでに `done_reason` を受け取り、`hit_limit` として警告に使っている
- `modernize_detailed()` のループは、例外が出たチャンクを原文のまま採用して次へ進む（`keep_original`）。`abort` なら例外をそのまま上げる。Ctrl+C は残りを原文のまま残して `aborted=True` で抜ける
- 開始時の `_check_model_available()` で、Ollama が最初から止まっているときはすぐ失敗する。G9 で困るのは「途中で固まる」（1 チャンク 300 秒待って時間切れ）場合だけ。途中で落ちた場合は接続エラーがすぐ返るので、待ち時間は問題にならず警告が並ぶだけ
- OCR 側の連続失敗の打ち切り（`scripts/ocr_vision_llm.py` の `_ocr_pages`）: 反復による失敗は数えず、連続の数を戻しもしない。成功で 0 に戻る
- Ollama の挙動（2026-11-23 に 0.40.17 で確認、`survey/batch-slow-failure-survey.md` と Ollama のソース）
  - この Mac は VRAM 17.8GiB と判定され、既定の `num_ctx` は 4096（23GiB 以上なら 32k、47GiB 以上なら 256k）。`OLLAMA_CONTEXT_LENGTH` でも変わる
  - 生成が上限に達したときの既定は context shift（古いトークンを捨てて生成を続ける）。ただし画像を読む部品（Projector）付きのモデルは context shift をせず、止まって `done_reason=length` を返す。qwen3.5:9b は Projector 付き（`ollama show` で vision・clip を確認）。glm-ocr では実際に length で止まることを G12 で確かめたが、qwen3.5 ではまだ確かめていない
  - 入力が `num_ctx` を超えると、既定（`truncate=true`）では古いメッセージから黙って落とす。system と最新のメッセージは残るので、落ちるのはお手本（few-shot）
  - 同じモデルを別の `num_ctx` で呼ぶと、モデルが読み込み直される

## Goals / Non-Goals

**Goals:**
- 上限で途切れた訳を、成功として記録に入れない
- Ollama が途中で固まっても、待ち時間を「タイムアウト × 打ち切りの数」までに抑える
- 既存の失敗の流れ（原文のまま残す・`failed_chunks`・終了コード 2・`abort`）に合流させ、`meta.json` の形と呼び出し側を変えない

**Non-Goals:**
- 入力が `num_ctx` を超えてお手本が落ちる場合の検知。既定の 2,000 字なら入力は約 2,300 トークンで起きない。`chunk.size` を大きくした人向けに `config.toml` のコメントで注意するだけにする
- 分割の再帰（4 分割・8 分割…）。理由は D2
- 半分だけ訳せた断片の部分採用。理由は D2
- 口語化の速度の改善、チャンク間の文脈の引き継ぎ（B4）
- OCR 側（`[ocr]`）の `num_ctx`。広げると反復が長く続くだけなので触らない（G12 の実測）

## Decisions

### D1. 溢れは `done_reason == "length"` で見分ける

Ollama への送信を新しい `_request()`（本文と `done_reason` を返す）に移し、`_chat()` は今までどおり本文を返す。`done_reason` が `length` なら `_chat()` が新しい例外 `ChunkOverflowError` を投げる（D2 の分割に回し、分けても溢れたら呼び出し元へ投げる）。

- 判定はお手本の混入の判定（G14）より**先**に行う。途中で途切れた訳に混入の判定をかけても意味がないため
- 却下した案: 入力と出力のトークン数の合計（`prompt_eval_count + eval_count`）が `num_ctx` に近いかで判定する。Ollama はお手本の部分をキャッシュして使い回すと入力のトークン数を少なく報告することがあり、当てにならない。`num_ctx` を明示しないと比べる相手の値もわからない
- 前提: qwen3.5 が上限で止まって `length` を返すこと（Context 参照）。タスク 1.1 の実験で最初に確かめる。もし context shift が起きて `length` が返らないなら、この設計の前提が崩れるので、実装に入る前に設計を見直す

### D2. 溢れた断片は 1 回だけ半分に分け、片方でも溢れたら断片全体を原文のまま残す

```
_modernize_chunk(chunk)
  |
  +-- お手本つきで変換 -------- length? --yes--> 半分に分ける（1 回だけ）
  |                                              |
  |   no                                         +-- 前半を変換（お手本つき → 混入なら お手本なし）
  |   |                                          +-- 後半を変換（同上）
  |   v                                          |
  +-- 混入? --yes--> お手本なしで変換            +-- どちらかが length --> ChunkOverflowError
  |   |                 |                        |                         （断片全体を原文のまま）
  |   no               length? --yes--> 半分へ   +-- 両方 OK --> 前半 + 後半 をつないで採用
  v
  採用
```

- **分け方**: 新しい `_split_in_half(text)` で、文の真ん中にいちばん近い「。」の直後で 2 つに切る。「。」が無ければ「、」か改行、それも無ければ字数の真ん中で切る。切るだけで字は足さないので、2 つをつなぐと元の断片と一字も違わない（既存の要件「分割で原文に字を足さない」を守る）。既存の `_split_text(size=半分)` を使い回さないのは、文の長さが不ぞろいだと 3 つ以上に分かれることがあり、「2 つに分ける」と言えないため
- **つなぎ方**: 切れ目に改行があった（前半の末尾か後半の先頭が改行）ときだけ改行 1 つでつなぎ、「。」「、」や字数の真ん中で切ったときは何も挟まずにつなぐ。原文に無い改行を段落の途中に入れないため（レビュー指摘 2。当初は常に改行 1 つでつなぐ計画だった）
- **空白だけの半分**: 分けた片方が空白・改行だけなら LLM に送らず、そのまま残す。空の入力に LLM が原文に無い文を作るのを防ぐ（レビュー指摘 3）
- **1 回だけにする理由**: 2,000 字で溢れる原因は「訳が少し長い」こと。半分（約 1,000 字、入力約 1,300 トークン）なら出力に約 2,800 トークン使えるので、普通の訳なら必ず収まる。それでも溢れるなら LLM が同じ文を繰り返している可能性が高く、さらに分けても時間を使うだけ
- **断片全体を原文に戻す理由**: 片方だけ訳せたときにそれを採用すると、「チャンクの一部だけ訳されている」という新しい状態ができる。`ChunkFailure`・`failed_chunks`・`prewar diff` の見え方まで考え直すことになるので、既存の「失敗した断片は原文のまま」に合流させる。溢れが 2 回続くのはまれで、捨てる訳は半分（約 1,000 字分）にとどまる
- お手本の混入で変換し直した結果（お手本なし）が溢れた場合も、同じく半分に分ける。このとき半分も**お手本なし**で送り、判定もしない（お手本つきに戻すと混入→変換し直しを半分ごとに繰り返し、1 チャンクで最大 6 回送ることになる。レビュー指摘 4）。お手本つきの最初の変換が溢れた場合は、半分もお手本つきで始め、混入の判定と変換し直し（G14）を通常どおり行う
- 失敗の番号（`ChunkFailure.index`）とチャンク総数（`chunk_total`）は分ける前の断片で数える。分けても数は増やさない
- 却下した案: (a) 途中までの訳を採用して警告するだけ → 字が欠ける。「文字を消さない」に反する。(b) 分けずにすぐ原文のまま残す → 実装は小さいが、普通の資料でも溢れた断片が訳されずに残る（explore で利用者が A 案を選んだ）

### D3. 連続失敗の数え方は OCR 側と同じにする

- 設定キーは `chunk.abort_after_consecutive_failures`（既定 3、0 以下で無効）。`batch.` 側と同じ名前と既定値にして、`[chunk]` の中にあることで口語化の設定だとわかるようにする
- 数えない例外: `FewShotLeakError`・`OllamaRepeatError`・`ChunkOverflowError`。どれも断片の中身が原因で、次の断片は成功しうる。数えない失敗では連続の数を戻さない（OCR 側と同じ。時間切れ → 反復 → 時間切れ…が続いても打ち切れるように）
- 数える例外: それ以外すべて（時間切れ・接続エラー・不明なエラー）。数えないものを列挙して、ほかは数える形にする。知らない種類のエラーは Ollama 側の問題である可能性が高く、打ち切る側に倒すほうが安全なため。OCR 側の `_NOT_COUNTED_AS_CONSECUTIVE` と同じ考え方
- 成功（お手本なしで変換し直して成功した場合や、分けて成功した場合を含む）で 0 に戻す
- `on_error = "abort"` のときは 1 回目の失敗で中止されるので、この設定は関係ない
- 却下した案: 時間切れのたびに Ollama の生存確認（`/api/version`）を挟み、応答が無ければすぐ打ち切る。原因の切り分けは正確になるが、OCR 側と仕組みが分かれ、テストも増える。既定 3 なら最悪でも 15 分で止まるので、まずは同じ仕組みにそろえる

### D4. 打ち切った残りは `failures` に 1 件ずつ足し、`meta.json` の形は変えない

- 打ち切ったら、残りの断片を原文のまま `modernized_chunks` に足す（Ctrl+C と同じ）。あわせて断片ごとに `ChunkFailure(index, "連続失敗で打ち切ったため未処理")` を足す。`failed_chunks` は `len(failures)` なので、呼び出し側を変えずに未処理の分も数に入る。終了コードも既存の「失敗チャンクがあれば 2」になる
- 画面には、打ち切りの行を 1 行だけ出す（「⚠ 連続 3 件失敗したため口語化を打ち切ります（未処理 4 チャンクは原文のまま）」）。残りの断片ごとの警告は出さない
- `ModernizeResult.aborted` は立てない。`aborted` は Ctrl+C の意味で使われ、`meta.json` の `error = "interrupted"` になるため
- 却下した案: `meta.json` に打ち切りの理由のキー（`error = "consecutive_failures"` など）を足す。どの断片が原文のままかは `failed_chunks` と画面でわかり、OCR 側のページの打ち切りも理由のキーは持っていない。「問題があったときだけキーを足す」原則に反しないが、足す理由が弱い

### D5. `num_ctx` は実験してから決める（明示する方向）

- 候補は `[llm] num_ctx = 8192` を `_DEFAULTS` に足すこと。`[llm]` はそのまま Ollama の options に渡るので、コードの変更は要らない。口語化は毎回同じ値で呼ぶので、読み込み直しは最初の 1 回だけ
- 明示する理由: Ollama の既定は VRAM の量・Ollama の版・環境変数で変わる。G4 で temperature を固定したのと同じく、環境が変わっても挙動が変わらないようにする
- 気になる点: 調査では 4096 → 8192 で 1 チャンク 110 秒 → 135 秒だった。ただし計測にモデルの読み込みが混ざった可能性がある。qwen3.5 は文脈を覚えるメモリが小さい作りなので、遅くならない見込みもある
- **決め方**（タスク 1.2）: 実際の 2,000 字のチャンクを 4096 と 8192 でそれぞれ 3 回変換し、2 回目以降（読み込みの済んだ状態）の時間と、`ollama ps` のメモリを比べる。遅くなるのが 1 割以内でメモリに余裕があれば 8192 を既定にする。そうでなければ明示せず、D1・D2 の検知と分割だけに頼る。どちらでも仕様は変わらない
- **結果と決定**（2026-11-23、Ollama 0.40.17、1,863 字のチャンク・入力 2,061 トークン、各 3 回）: 読み込み済みの 2・3 回目の 1 トークンあたりの時間は 4096 で 56.5・57.5 ms、8192 で 56.2・56.3 ms と同じだった。
  8192 の方が 1 回あたりの時間が長く見えたのは、訳が長かった（出力 1,235〜1,531 トークンと毎回揺れる）ため。`ollama ps` のメモリは 1.4GB → 1.7GB。基準を満たすので **`[llm] num_ctx = 8192` を既定にする**。
  なお 4096 では合計が最大 3,592 トークン（88%）に達し、2,000 字ちょうどのチャンクなら溢れうることも確かめられた。上限で止まることはタスク 1.1（`num_ctx` 2,600）で確認した（llama.cpp が 256 の倍数に切り上げた 2,816 トークンで `length`）
- **`num_predict` も明示する**（レビュー指摘 1、2026-11-23）: 8192 では訳に使える残りが約 6,100 トークンあり、56ms/トークンで出し切るには約 340 秒かかる。
  時間切れ（300 秒）の方が先に来るので、LLM が同じ文を繰り返し続ける暴走では `length` に届かず、分割が働かない。しかも時間切れは連続失敗に数えるので、
  暴走するチャンクが 3 つ続くと Ollama が正常でも打ち切られる。そこで `[llm] num_predict = 3072`（訳のトークン数の上限）を既定にし、最長でも約 170 秒で `length` に止める。
  実測の最長の訳（1,531 トークン）の 2 倍あり、普通の訳は切らない。入力（約 2,300）＋3,072 は 8192 に収まる。OCR 側の `num_predict`（G12）と同じ仕組みで、0 以下なら渡さない。
  値は `int()` に直してから渡す（`"8192"` のように文字列で書かれても Ollama で型エラーにしない。レビュー指摘 5。OCR の `num_predict` も同じに直す）
- 却下した案: `chunk.size` を 1,500 字に下げる。断片の境目が 3 割増え、文脈が途切れる箇所（B4）が増える。お手本を毎回送る分の負担も増える

### D6. 反復検知の文言を OCR と口語化の両方で読めるようにする

`ollama_errors()` の `OllamaRepeatError` の文言「OCRエンジンが同じ内容を繰り返したため…」を「モデルが同じ内容を繰り返したため…」のように主語をモデルにする。`ollama_errors()` にはモデル名が渡るので、文言にモデル名を入れて区別する。OCR 側の分類（`reason: "repeat"`）とテストの期待値は文言に依存していないことを確認する。

### D7. テスト用フェイクは `done_reason` も返せるようにする

`tests/fakes.py` の `ScriptedChatModernizer` の差し替え先を `_chat()` から `_request()` に移し、応答の列の要素に「文字列（`stop` とみなす）」「(文字列, done_reason)」「例外（投げる）」を書けるようにする。溢れの判定（`_chat()`）は本物のコードを通る。既存のテストは書き換えずに通るようにする。`unittest.mock` は使わない（プロジェクトの決めごと）。

実装中の変更: 当初は `_chat()` の戻り値を (本文, done_reason) に変える計画だった。しかし既存のテストに `_chat()` を差し替えて文字列を返す子クラスが 3 つあり（`_RecordingModernizer`・`_LeakingModernizer` と旧 `ScriptedChatModernizer`）、戻り値を変えると全部書き換えになる。`_chat()` の約束（本文を返す）を保ったまま送信を `_request()` に分けたので、書き換えずに済んだ。

## Risks / Trade-offs

- [qwen3.5 が上限で止まらず context shift する] → 溢れを検知できない。タスク 1.1 で最初に確かめ、起きるなら実装の前に設計を見直す（D1）
- [Ollama の更新で Projector 付きモデルの挙動が変わる] → Ollama は自動更新される。タスク 1.1 の確かめ方を `survey/` に残し、挙動が怪しいときに繰り返せるようにする
- [分けても溢れた断片の、訳せた半分を捨てる] → 起きるのはまれ（D2）。捨てても原文は残るので字は欠けない
- [打ち切りの既定 3 では、固まってから止まるまで最大 15 分（300 秒 × 3）かかる] → 従来の「残り全部 × 300 秒」よりは大幅に短い。急ぐ人は `ollama.generate_timeout_seconds` か打ち切りの数を下げられる
- [未処理の断片も `failed_chunks` に数えるので、「失敗」の数が LLM の失敗回数より多くなる] → 画面の打ち切りの行で内訳がわかる。`meta.json` を見る人にとっては「原文のまま残った断片の数」として一貫する
- [`num_ctx = 8192` でメモリが足りないとき] → 24GB 機で他のアプリが多いとモデルが追い出される（調査 1-3）。タスク 1.2 でメモリを測ってから決める。`config.toml` で `[llm] num_ctx = 0` にすれば Ollama の既定に戻せる（`num_ctx` を `_DEFAULTS` に置いたので、行を消しても 8192 のまま。OCR の `num_predict` と同じく 0 以下は渡さない形にした）

- [`num_predict` 3,072 を超える正当な長い訳] → `length` になり半分に分けて変換し直すので、字は欠けない（時間が 1 回分余計にかかるだけ）

## Migration Plan

- 新しい設定はどれも既定値を持つので、`config.toml` を書き換えなくても動く。既存の記録・索引は作り直さない
- 打ち切りの仕組みが不要なら `chunk.abort_after_consecutive_failures = 0` で従来の挙動に戻る
- `num_ctx` は `config.toml` の `[llm]` に別の値を書けば上書きでき、`0` なら Ollama の既定に戻る
