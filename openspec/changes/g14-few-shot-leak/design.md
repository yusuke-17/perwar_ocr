# Design

## Context

動機は proposal.md の Why を参照。ここでは方針を決めるのに要る現状だけを書く。

- `TextModernizer._build_messages`（`utils/text_modernizer.py`）は、`SYSTEM_PROMPT` のあとに `FEW_SHOT_EXAMPLES` の 3 例を user / assistant の往復として並べ、最後に本物のチャンクを user として渡す。LLM から見ると「3 往復した会話の続き」になっている
- 混入した文は**お手本の出力と一字一句同じではない**。2026-11-03 に見つかった文は「その流派の**開祖**は常陸国…」で、お手本の出力は「その流派の**創始者**は…」。モデルはお手本の**入力を訳し直して**いる
- 口語化の生成パラメータは `temperature: 0.5`（`_DEFAULTS["llm"]`）。同じチャンクでも毎回結果が揺れ、混入も 6 回中 3 回と確率的に起きた
- チャンクの変換が例外で終わると、`modernize_detailed` がそのチャンクを原文のまま採用して `failures` に記録する（G2）。`prewar ocr` は件数を画面に出して `meta.json` の `failed_chunks` / `chunk_total` に書き（`library_writer.py`）、`prewar fix` は件数を画面に出す。`chunk.on_error = "abort"` なら例外をそのまま投げ直す
- テストは `_chat`（LLM への送信）か `_modernize_chunk` を差し替えた子クラスで書いている（`tests/test_text_modernizer.py`・`tests/test_modernize_resilience.py`）。`unittest.mock` は使わない

```
modernize_detailed
  for chunk:
    try:
      _modernize_chunk(chunk)                  <-- この中に「検出 -> 再試行」を入れる
        result = _chat(お手本つき)
        混入なし --> return result
        retry_without_examples:
          画面に 1 行、return _chat(お手本なし)   <-- 判定せずに採用
        else:
          raise FewShotLeakError               <-- 既存の except Exception に合流
    except Exception:  原文のまま採用 / abort なら投げ直す   (既存)
```

## Goals / Non-Goals

**Goals:**
- 混入の判定を「原文に無い、お手本由来の語」の有無で行い、原文が実際に憲法や勅語を引用している場合を見逃す（採用する）
- お手本なしでの変換し直しと、変換し直さない設定のときに原文のまま残す処理を `_modernize_chunk` の中に閉じ込め、`modernize_detailed`・呼び出し側・`meta.json` の形を変えない
- お手本の文面を将来変えたときに、目印の付け忘れをテストで気づけるようにする

**Non-Goals:**
- プロンプトの組み立て方や文面を変えて、混入の頻度そのものを下げること（比較実験が要るため別の変更にする）
- お手本以外の「原文に無い文」（LLM の創作・要約）の検出
- 混入した文だけを削って残りを採用すること
- 既存の記録の口語化テキストを検査し直すこと

## Decisions

### D1: 混入は「目印の語の組」で判定する

お手本ごとに目印の組（`LeakMarker`）を持たせる。1 つの組は次の 2 つから成る。

- **出力側の語**（`output_terms`）: 変換結果に**すべて**含まれたら、そのお手本を訳し直した疑いがある
- **原文側の語**（`source_terms`）: チャンクの原文に**どれか 1 つでも**あれば、本物の引用とみなして混入としない

判定は「どれかの組で、出力側の語がすべて結果にあり、原文側の語が 1 つも原文に無い」とき混入とする。

| お手本 | 出力側の語（すべて） | 原文側の語（どれか） | 強さ |
|---|---|---|---|
| 例 1（憲法・納税） | `日本の国民は` ＋ `税金を納める義務` | `臣民` `税` `稅` | 弱い語どうしを組にして強める |
| 例 2（流祖） | `常陸` | `常陸` | 強い（固有名詞） |
| 例 2（流祖） | `心影流` | `心影流` | 強い（固有名詞） |
| 例 3（教育勅語） | `皇室の祖先` | `皇祖` `皇宗` `祖宗` `列聖` `皇考` | 強い |

原文側の語は、レビューの指摘で広げた。「國民」と「租税」で書かれた本物の租税の文や、「祖宗ノ遺訓」のように「皇祖」以外の語から「皇室の祖先」と訳される文を、混入と誤判定しないため。例 1 は原文に「税」が 1 字でもあれば本物の訳とみなす。

- 例 1 は固有名詞が無い。「税金を納める義務」だけで判定すると、租税を扱う公文書の正しい訳を誤って混入とみなしてしまう。そこで、実際に混入した文が含んでいた 2 つの言い回しが**両方**出たときだけ判定する
- 原文側の語は、正規化を通さない `prewar fix --no-normalize` 相当の入力も考えて旧字体も並べる（`稅`）。`常陸` `心影流` `皇祖` `臣民` などは旧字体と新字体で字が同じ
- 目印はお手本の文面と一緒に変わるものなので、`FEW_SHOT_EXAMPLES` の各例の隣（`"leak_markers"` キー）に置く。`config.toml` には出さない。`_build_messages` は `input` / `output` しか読まないので、キーを足してもプロンプトは変わらない

検討した代案:
- **お手本の出力との完全一致・部分一致**: 実際の混入は訳し直しなので一致しない。不採用
- **文字の n-gram の類似度**: しきい値の調整が要り、何が起きたかを説明しにくい。目印の組なら判定理由を画面に出せる。不採用
- **目印を `config.toml` に出す**: お手本の文面はコードにあるので、片方だけ書き換えて食い違う恐れがある。不採用

### D2: 混入したらお手本なしで 1 回変換し直し、その結果は判定せずに採用する

`_modernize_chunk` はこれまでどおりお手本つきで変換する。混入していたら、`SYSTEM_PROMPT` とチャンクだけのメッセージ（お手本なし）で 1 回変換し直し、その結果をそのまま返す。

- お手本つきの経路は変えない。お手本は「だ・である」調や言い換えの度合いを揃えるために入れているので、混入の無いチャンク（大半）の訳の質は今と同じに保つ
- お手本なしなら、お手本の文はそもそも LLM に渡らないので混入は起きようがない。そこで判定に掛かるのは誤判定だけ（例: 教育勅語の引用がチャンクの境目で切れ、「皇祖」が前のチャンクにある）なので、判定せずに採用して正しい訳を捨てない
- 設定は `_DEFAULTS["chunk"]["retry_without_examples"] = True`。チャンク単位の振る舞い（`on_error` と同じ節）なので `[chunk]` に置く。お手本なしの結果を判定しない以上、回数を選ぶ意味は無いので真偽値にした
- 変換し直すときに画面へ 1 行出す（例「    ⚠ お手本の例文の混入を検出（常陸）。お手本なしで変換し直します」）。進捗バーの表示中でも、既存の失敗の警告と同じく `print` で出す（rich の進捗バーは表示中の標準出力をバーの上に出すので崩れない）

**経緯 1（2026-11-15 の実機確認）**: 当初は「お手本つきのまま既定 2 回変換し直す。`temperature: 0.5` の揺れで混入の無い結果が出る」と見込んでいた（混入率 50% なら 3 回とも混入は約 12.5%）。
`input/1.png`〜`10.png` の記録を 3 回作ると、3 回とも 2 つ目のチャンクで、3 回の変換すべてに混入が出た。お手本の例 2（流派の由来）とこの資料の話題が同じで、話の途中から始まるチャンクの「冒頭」として、例 2 の訳がほぼそのまま前に付く。
再試行では直らず、そのチャンク（記録の約半分）が口語化されないまま残った。同じチャンクをお手本なしで 2 回変換すると、2 回とも混入せずに最後まで訳せた（約 80〜100 秒）。お手本なしで変換し直す形に改めた後は、3 回とも 1 回の変換し直しで混入が消えた。

**経緯 2（2026-11-15 のコードレビュー）**: 改めた直後は、お手本なしの結果にも判定をかけ、引っかかれば最大 `retry_on_leak` 回まで変換し直して、だめなら原文のまま残していた。
レビューで「お手本なしの結果に掛かるのは誤判定だけで、正しい訳を捨ててしまう」と指摘され、利用者と相談して判定せずに採用する形にした。

検討した代案:
- **お手本つきのまま変換し直す（当初案）**: 経緯 1 のとおり、話題が重なる資料では直らない。不採用
- **お手本なしの結果にも判定をかける**: 経緯 2 のとおり、誤判定で正しい訳を捨てる。不採用
- **最初からお手本を外す**: 混入は根絶できるが、全チャンクの訳の質と文体が変わる。比較実験が要るので範囲外。不採用
- **お手本の例 2 を別の話題に差し替える**: 混入の起きやすさは下がる見込みだが、プロンプトの変更で比較実験が要る。改善案 B5 として残す
- **`modernize_detailed` のループで再試行する**: チャンクの失敗処理と再試行が混ざって読みにくくなる。`_modernize_chunk` に閉じ込めれば、外から見ると「成功したか、例外を投げたか」のどちらかで変わらない。不採用

### D3: 変換し直さない設定では専用の例外を投げ、既存の失敗の流れに合流させる

`FewShotLeakError(Exception)` を `utils/text_modernizer.py` に足す。`retry_without_examples = false` のときに混入を見つけたら投げる。メッセージは「お手本の例文が混入しました（常陸）」のように、判定に使った語を含める（`abort` のときも意味が通るよう、「原文のまま残す」とは書かない）。

- `modernize_detailed` の既存の `except Exception` が受けて、原文のまま採用し `ChunkFailure` に記録する。画面には既存の「⚠ チャンク i/n の変換に失敗（原文のまま）: <メッセージ>」が出るので、理由が混入であることが分かる
- `meta.json` には `failed_chunks` として数えられる。理由の文字列は保存しない（既存の失敗も保存していない。保存形式を変えない）
- `on_error = "abort"` では、既存どおり投げ直されて変換全体が中止になる
- `KeyboardInterrupt` は変換し直しの途中でもそのまま上に伝わり、既存の中断処理が働く

検討した代案: **混入した文だけを削る**。どこまでが混入かを文単位で正しく切れる保証が無く、本物の訳を削る恐れがある。「文字を消さない」原則に反する。不採用。

### D4: お手本と目印の整合はテストで守る

`FEW_SHOT_EXAMPLES` の各例について、次をテストで確かめる。

- 少なくとも 1 つの目印の組を持つ
- その例の `output` を、関係の無い原文（例「陸軍省ハ左記ノ通リ通牒ス。」）に対する変換結果とみなすと、混入と判定される
- その例の `input` を原文とし、`output` を変換結果とみなすと、混入と判定されない（本物の引用は見逃す）

お手本を差し替えて目印を付け忘れると、このテストが落ちる。

## Risks / Trade-offs

- [目印に掛からない言い回しで混入する（例「日本国民は法に従い納税の義務を負う」）] → 目印は実際に混入した文から選んでいるが、網は完全ではない。新しい形の混入を見つけたら目印の組を足す。目印はコードの 1 か所にまとまっている
- [お手本つきの結果の誤判定（原文側の語が無い本物の訳。引用がチャンクの境目で切れた場合など）] → お手本なしで変換し直した結果が採用されるので、失うのは LLM の呼び出し 1 回分だけ。原文側の語はレビューを受けて広げた（D1）
- [お手本なしの結果に、お手本とは無関係な創作の文が混ざる] → この変更では検出しない（Non-Goals）。お手本つきの経路と同じ条件で、新たに増える危険ではない
- [原文が「常陸」を含み、かつ別のお手本が混入する] → 「常陸」の組は見逃すが、ほかのお手本の目印（`皇室の祖先` など）が残っていれば判定できる。両方が重なる場合は見逃しうる。まれなので受け入れる
- [混入したチャンクの処理時間が増える] → LLM の呼び出し 1 回分（1,500 字前後のチャンクで約 80〜100 秒）。混入が無いチャンクには影響しない
- [お手本なしの訳は、お手本つきと文体や言い換えの度合いが少し違うことがある] → そのチャンクだけの差で、原文に無い文が混ざるよりはるかに害が小さい。お手本の差し替えで最初の変換の混入を減らす案は改善案として残す
- [話題がお手本と重なる資料では、最初の変換がほぼ毎回むだになる] → 1 チャンクあたり LLM の呼び出し 1 回分の損。お手本の例 2 を差し替えれば減らせる見込み（同上）

## Migration Plan

設定の追加（既定値あり）だけで、保存形式・索引・依存は変わらない。`config.toml` に `retry_without_examples` を書かなくても既定の true が効く。
既存の記録は作り直さない。混入が疑わしい記録は `prewar fix` で口語化し直すか、OCR し直す。
元に戻すときは、このブランチの変更を取り消せばよい。`config.toml` に `retry_without_examples` を書いていても、旧版は知らないキーを無視する。
