## Context

動機は proposal.md の Why を参照。現状のコードとデータで確かめた事実（2026-11-03）:

- 変換表は `pkg/senzen_word/src/senzen_word/kanji/data/` の 3 つの JSON（`joyo_old_new.json` 372 字・`jinmei.json` 9 字・`variants.json` 3 字）。`converter.py` が順に `dict.update` で統合し、`str.translate` で 1 字ずつ置き換える。値が別のキーになっている「連鎖」は今は無いが、検査するテストも無い。
- パイプラインでは `normalize_text` が senzen_word の前に NFKC をかけるので、互換漢字（`海` U+FA45 など）は senzen_word に届く前に統合漢字になる。今回追加する 42 字はどれも NFKC で変わらないことを確かめた。
- 検索索引（`utils/library_search.py` の原文カラム）と差分表示（`scripts/diff_viewer.py`）は、保存済みの `ocr_raw.txt` に `normalize_text` をかけ直す。規則を変えたら `INDEX_SCHEMA_VERSION`（現在 2）を上げる決まりがあり、版が違うと索引は自動で作り直される。
- 版が 2 であることを固定で確かめるテストが 2 つある（`tests/test_text_normalizer.py::test_index_schema_version_is_not_raised`、`tests/test_library_search.py::test_schema_version_unchanged_by_query_expression_change`）。
- NDLOCR-Lite の出力文字集合は `vendor/ndlocr-lite/src/config/NDLmoji.yaml`（7,141 字、うち漢字 6,599 字）。追加する 42 字はすべて含まれる。既存の `﨑` `髙` は含まれず、OCR からは出ない。
- Unihan（Unicode 18.0.0）の異体字 5 項目（kZVariant・kSemanticVariant・kSpecializedSemanticVariant・kSimplifiedVariant・kTraditionalVariant）を双方向に辿ると、NDLOCR-Lite の文字集合のうち常用・人名用漢字と結び付く非常用の字は 381 字。今回の 42 字を足した後も、未判断は 257 字残る。
- 一方 Unihan は既存の表の 322 字のうち 275 字を結び付けられず、今回の 42 字のうち 8 字（`閱尙產姬旣淸靑鬪`）も拾えない。

## Goals / Non-Goals

**Goals:**
- 変換表の出典ごとにファイルを分け、どの字がどの根拠で入ったかを追えるようにする
- 変換表どうしの食い違いと連鎖を、テストで機械的に防ぐ
- OCR エンジンや Unihan が更新されたとき、判断が要る字を監査ツールで洗い出せるようにする

**Non-Goals:**
- 監査ツールを毎回のテストで走らせること（Unihan の取得が要るため。手動で実行する）
- Unihan が結び付けない旧字の網羅（監査は再発を減らす網で、完全ではない。Risks を参照）
- 変換表を Unihan から自動生成すること（D1）

## Decisions

### D1. 変換表は人が判断し、機械は「判断漏れの検出」と「整合性の検査」だけを担う

- 採用: 変換する字は人が 1 字ずつ確かめて JSON に書く。機械は (a) 判断していない候補の列挙（監査ツール）と (b) 表の整合性（テスト）を担う。
- 却下: Unihan からの機械生成（G10 の当初案）。既存の 322 字のうち 80 字しか再現できず、`壹→一` `據→据` のような誤りが混ざる。Unihan は主に中国語の簡体字・繁体字の関係を記録しており、日本の新旧字体の対応とずれる。
- 却下: JIS や文字情報基盤（MJ 縮退マップ）を使う案。MJ 縮退マップは対応の質は高いが、ライセンスが継承条件付き（表示—継承）で、MIT の senzen_word に派生データを入れると条件が衝突する。

### D2. 追加する字はファイルを分けて置く

- `kanji/data/glyph_old_new.json`（新規）: 常用漢字表に括弧書きされない字形違いの旧字 35 字（提案時の 34 字と、監査で見つけた `栅→柵`）。
- `kanji/data/zokuji.json`（新規）: 俗字・略字 42 字（提案時の 8 字と、監査で見つけた `甞→嘗` `禀→稟` `决→決` など 34 字）。
- `kanji/data/variants.json`（既存）: 監査で見つけた異体字 72 字（`卻→却` `攜→携` `羣→群` など）を足して 75 字。俗字（略した形）と異体字（正字や別の構成の形）を分けて置く。
- 既存の `joyo_old_new.json` は「常用漢字表準拠」のまま触らない。出典の違う字を混ぜると、表の正しさを公式の表と照合できなくなるため。
- 読み込み順は `joyo_old_new` → `glyph_old_new` → `zokuji` → `jinmei` → `variants`。キーが重ならないことをテストで保証するので、順序は結果に影響しない。

### D3. 「変換しない字」の一覧は開発用ツールの側に置く

- `pkg/senzen_word/tools/kanji_keep.json`（新規）。パッケージ本体には入れない（実行時に使わないため）。
- 形式: `{"嵜": {"reason": "人名地名", "note": "崎の異体字"}, ...}`。`reason` は次のどれか:
  - `人名地名`: 人名・地名に使われる異体字（`嵜` `碕` など）
  - `簡体字`: 中国の簡体字。OCR の誤読の可能性が高い（`个` `从` など）
  - `別字`: Unihan では結び付くが、日本語では別の字として使う、または結び付きが誤り（`拯` `窕` など）
  - `書きかえ`: 「同音の漢字による書きかえ」に当たる語の置き換え（`慾→欲` など）
  - `保留`: 判断に資料の用例が要るもの。理由を `note` に書く
- `note` には、結び付く常用・人名用漢字と判断の根拠を短く書く。

### D4. 監査ツールの仕様

- 置き場: `pkg/senzen_word/tools/audit_kanji_table.py`（`gen_hentaigana.py` と同じく開発用。標準ライブラリだけで書く）。
- 入力:
  - `--charset PATH`（必須）: OCR の出力文字集合を含むファイル。ファイル中の全文字を集合として扱う。プロジェクトでは `vendor/ndlocr-lite/src/config/NDLmoji.yaml` を渡す。senzen_word を NDLOCR-Lite に依存させないため、パスは引数で受け取る。
  - `--unihan PATH`（任意）: Unihan.zip のパス。省略時は Unicode 公式サイトから版を固定した URL（18.0.0）で取得し、`pkg/senzen_word/tools/.cache/` に保存して再利用する（`.cache/` は `.gitignore` に入れる）。取得するのは公開データだけで、資料は送らない。
- 候補の定義: 文字集合の字のうち、CJK 統合漢字で、常用漢字（kJoyoKanji）でも人名用漢字（kJinmeiyoKanji）でもなく、NFKC で変わらず、異体字 5 項目を双方向に辿って常用・人名用漢字に結び付く字。
- 未判断 = 候補 − 変換表のキー（`get_kanji_table()` で実際に読み込まれる表）− `kanji_keep.json` のキー。
- 出力: 未判断の字を 1 行ずつ、結び付く常用・人名用漢字と、簡体字の目安（kTraditionalVariant を持つか）を添えて表示し、最後に件数を出す。未判断が 1 字以上なら終了コード 1、0 字なら 0。

### D5. 整合性はパッケージのテストで検査する

`pkg/senzen_word/tests/test_kanji.py` に足す:
- 5 つの JSON を横断して、同じキーが 2 つのファイルに無い
- 変換先がどの表のキーでもない（連鎖が無い。`convert_old_kanji` を 2 回かけても変わらないことと同値）
- `kanji_keep.json` のキーが変換表に無く、`reason` が D3 の 5 種のどれか
- 追加した 42 字の変換と、`嵜` `碕` が変わらないこと

### D6. 検索索引の版を 3 に上げる

`INDEX_SCHEMA_VERSION` を 3 にする。版が 2 であることを固定で確かめていた 2 つのテストは、それぞれの変更（ページ境界・検索構文）で版を上げなかったことの記録なので、値を 3 に更新し、docstring に「G10 で 3 に上げた」と書き足す。

## Risks / Trade-offs

- [Unihan が結び付けない旧字は監査に出ない（今回の 8 字や既存表の大半がそう）] → 監査は「再発を減らす網」と README に明記する。今後 OCR 結果で見つけた旧字は、手で変換表に足し、テストに 1 行加える。
- [俗字の `蘆→芦` は人名（徳冨蘆花など）にも当たる] → 利用者の判断（俗字は入れる）に従う。人名だけの異体字（`嵜` `碕`）とは扱いを分けた。
- [`彥` は主に人名に現れる] → `彥` は `國` と同じ旧字形で、異体字ではない。既存の `晉→晋` `聰→聡` と同じく変換する。
- [257 字の判断は手間がかかり、誤判断も起こりうる] → `reason` を 5 種に絞り、迷う字は `保留` にして note に根拠を書く。保留は監査を通すが、一覧から後で見直せる。
- [索引の作り直しで初回の検索が遅くなる] → 既存の仕組みどおり一度だけ。資料ファイルは変えない。

## Migration Plan

1. 実装を入れると、次の `prewar search` / `prewar index` で版の違いが検知され、索引が自動で作り直される（「再構築」のメッセージが出る）。
2. 差分表示は `ocr_raw.txt` を毎回正規化し直すので、作業なしで新しい変換が反映される。
3. 戻すときは変更を取り消して版を 2 に戻せば、次の検索で再び作り直される。

## Open Questions

- 既存の `﨑→崎` `髙→高` `𠮷→吉`（`variants.json`）は、「人名・地名用の異体字は変換しない」方針と食い違う。`﨑` `髙` は NDLOCR-Lite から出ないので実害は小さい。方針をそろえるかは、仮名まわりの改善と合わせて後で決める。今回は振る舞いを変えない。
