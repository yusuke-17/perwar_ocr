## Context

動機は proposal.md - Why を参照。ここでは approach を決めるために必要な現状だけを書く。

現在の検索経路は3層に分かれている。

```
  scripts/library.py            utils/library_search.py           SQLite FTS5
  ─────────────────────         ────────────────────────          ──────────
  add_find_arguments()   ──→    _build_match_expr()        ──→    search MATCH ?
    query: nargs="+"              split(" ")                       tokenize='trigram'
                                  normalize_query() × 語
                                  3文字検査
                                  '"語"' AND '"語"'

  cmd_find()             ←──    search()                   ←──    snippet(-1,'[',']','...',16)
    抜粋を print                  SearchHit(snippet=...)            highlight() × 3 で一致判定
```

設計を縛る実測事実（SQLite 3.50.4 / trigram で検証済み）:

| # | 事実 | 影響 |
|---|---|---|
| 1 | `NOT` は二項演算子。`NOT "語"` 単独は構文エラー | 除外語だけのクエリは表現不能 |
| 2 | 優先順位は `NOT > AND > OR` | 括弧を自分で付けないと利用者の直感と食い違う |
| 3 | `{col} : "語"` でカラム限定が可能。未知カラム名は `no such column` エラー | カラム名の検証が必須 |
| 4 | `snippet()` の N は trigram だとほぼ文字数と1:1（N=64→71文字） | 長さ調整が素直に効く |
| 5 | `bm25()` は頻出語で全件ゼロ付近に潰れる（200件中196件ヒットで best/worst とも -0.000） | 序列として使えない |
| 6 | `highlight()` はカラム全文にマーカを入れて返す | 一致回数を数える材料になる |
| 7 | argparse の `nargs="+"` は `-大阪` を未知オプションとして飲み込む（`parse_args` ではエラー終了） | 記号による除外構文は使えない |
| 8 | trigram の3文字下限はすべての語に等しく効く | 除外語・限定語も検査対象 |

## Goals / Non-Goals

**Goals:**

- FTS5 の表現力を、**FTS5 の構文を利用者に見せずに**公開する。とくに事実2の優先順位は
  利用者の目に触れさせない
- 抜粋の強調を「意味（一致箇所）」と「表現（色・括弧）」に分離し、出力形式ごとに正しく変換する
- 索引に手を入れない。`INDEX_SCHEMA_VERSION` を据え置き、既存ライブラリの再構築を発生させない

**Non-Goals:**

- 括弧によるグループ化やネストした論理式。史料検索の実務で必要になる頻度に対して
  パーサの複雑さが釣り合わない
- 前方一致（`語*`）・近接検索（`NEAR`）。trigram tokenizer では意味を成さない、
  あるいは効果が読めない
- 抜粋の64文字超（Non-Goal の理由は Decision 5）

## Decisions

### 1. 演算子は記号ではなくキーワード（`OR` / `NOT`）

`-大阪` のような記号は採らない。事実7のとおり argparse が `-` 始まりの語をオプションとして
解釈し、`nargs="+"` の位置引数に届かない。`--` セパレータで回避できるが、
`uv run prewar search 関東 -- -大阪` は説明も打鍵も苦しい。

`!大阪` は argparse を通るが、zsh の履歴展開と衝突する余地が残る。

`OR` / `NOT` の大文字キーワードなら:

- argparse を素通りする（実測確認済み）
- シェルのクォートが不要
- 2つの演算子が対称になり、説明が1行で済む
- FTS5 自身の語彙と一致するため、将来 `--raw` を足すときも一貫する

日本語の資料本文に大文字 ASCII の `OR` / `NOT` が単独語として現れる見込みは薄い。
どうしても検索したい場合は将来クォートで逃がす余地を残す（今回は実装しない）。

**代替案**: `--not 大阪` の繰り返しフラグ。曖昧さゼロだが、対話メニュー（`_menu_search`）で
1行のテキスト入力から組み立てられないため採らない。

### 2. `OR` は演算子ではなく**モード切替**

```
  入力:  関東地方 OR 大阪府下 警察署
  ─────────────────────────────────────
  素直に流す:  "関東地方" OR ("大阪府下" AND "警察署")   ← 事実2。直感と違う
  本設計:      "関東地方" OR "大阪府下" OR "警察署"      ← OR が1つでもあれば全体がOR
```

検索語群のどこかに `OR` があれば、群全体を OR で結合する。混在を許さない。

こうすると、事実2の優先順位を利用者に一切説明しなくてよくなる。「ANDかORか」の
二択に落ちるので、ヘルプも1行で書ける。混在した論理式が必要になる場面は、
史料の絞り込みでは括弧が欲しくなる場面とほぼ同じで、そこは Non-Goal に置いた。

**代替案**: `OR` を真の二項演算子として扱い、`(A OR B) AND C` と解釈する。
利用者ごとに期待が割れる（左結合か、OR を弱く見るか）ため、
「説明できない挙動」を抱え込むより二択に倒す。

### 3. `NOT` 以降はすべて除外語、除外は最後に一括適用

```
  入力:  関東地方 震災被害 NOT 大阪府下 横浜港
  組み立て: ("関東地方" AND "震災被害") NOT ("大阪府下" OR "横浜港")
             └── 検索語群（Decision 2 でAND/ORが決まる） └── 除外語はOR
```

除外語同士を OR で束ねるのは「どれか1つでも含めば除く」が自然な期待だから。
検索語群を丸ごと括弧で包んでから `NOT` を当てることで、事実2の優先順位が結果に出ない。

除外語だけのクエリ（事実1）は `QuerySyntaxError` とし、「除外語だけでは検索できません」と伝える。

`NOT` は1回だけ現れる前提とし、2回目以降が現れたらエラーにする（黙って無視しない）。

### 4. カラム限定は別名を経由し、生の識別子を通さない

利用者が書くのは `原文:罹災者` / `original:罹災者`。区切りは半角 `:` と全角 `：` の両方を受ける
（日本語入力からそのまま打てるように）。

```
  別名表（コード内の定数）
    原文, 元, original  → original
    口語, 現代, modern  → modern
    題名, 表題, title   → title
```

別名表に無い語は `QuerySyntaxError` として、使える別名を並べて返す。事実3のとおり
未知のカラム名は SQLite の `no such column` として漏れるが、これを利用者に見せると
実装の内部（FTS5 のカラム名）が露出する。別名表で受け止めることで、
**利用者の入力が FTS5 の識別子として解釈される経路そのものを断つ**。

コロンを含むが別名に一致しない語（例: `午前10:30`）は、限定指定ではなく
ふつうの検索語として扱う。誤爆を避けるため「コロンの左が別名表にあるときだけ限定」とする。

**実装時の補足**: この規則だけだと「未知の対象名」を検知できず、
spec の `#### Scenario: 未知の対象名` を満たせないことが実装中に判明した。
そこで、コロンの左が **ASCII英字だけ**の語（`body:`、`orig:` 等）に限り
「対象名の書き間違い」とみなしてエラーにする。日本語の資料本文に `body:` のような
語が検索語として現れる見込みは無く、`午前10:30`（数字を含む）や日本語混じりの語は
従来どおり素の検索語に落ちるため、誤爆と検知の両立ができる。

除外語に対する限定（`NOT 原文:罹災者`）は受け付けない。除外は文書全体が対象という
仕様（spec「検索語の除外」）と食い違うため、黙って無視せずエラーにする。

### 5. 抜粋は `snippet()` の N を可変にし、64 で頭打ちにする

事実4より N はほぼ文字数として使える。既定を 16 から広げ、`--snippet` で実行時に変えられるようにする。

上限を 64 に固定するのは、SQLite の公式ドキュメントが `N` を「0 より大きく 64 以下」と
定めているため。手元の 3.50.4 は N=200 を通して 211 文字を返したが、
ドキュメントの範囲外の挙動に依存すると SQLite の版が変わったときに黙って壊れる。
仕様側も「上限を超える指定は上限に丸める」とした。

**代替案（今回は採らない）**: `highlight()` がカラム全文を返す性質（事実6）を使い、
マーカ位置の前後を Python で任意長に切り出す。64文字超が必要になったらこの手が使える。
今回は「16文字→最大64文字」で当初の不満が解消するため、複雑さを足さない。

### 6. 強調マーカは制御文字。表示層で ANSI、JSON 層で構造に変換

`library_search.py` には一致カラム判定用の `_MARK_OPEN = "\x02"` / `_MARK_CLOSE = "\x03"` が
すでにある。`snippet()` の開始・終了記号にも同じ定数を使い、`[` `]` を捨てる。

```
  library_search.search()
      snippet(search, -1, "\x02", "\x03", "…", N)
              │
              └─→ SearchHit.snippet = "\x02警察署\x03が誘導。…"
                        │
      ┌─────────────────┴──────────────────┐
      ▼                                    ▼
  text 出力 (scripts/library.py)      json 出力
    \x02 → ANSI 開始色                  マーカを除去した素の抜粋
    \x03 → ANSI リセット                 + 一致箇所の [開始, 終了) 位置リスト
    色OFF時は単に除去
```

これで JSON から `[ ]` が消え（proposal の BREAKING）、本文に元から角括弧がある資料でも
強調と混同されなくなる。

### 7. 一致回数は SQL 内でマーカを数える

`highlight()` の結果をそのまま Python へ運ぶと、20件 × 3カラム分のカラム全文が転送される。
SQL 内で数えれば整数3つで済む。

```sql
(length(highlight(search, N, mark, mark2)) - length(replace(highlight(...), mark, ''))) AS hits
```

実測で `d1 modern=3 original=1 title=1` のように取れることを確認済み。
既存の `instr(...) > 0` による一致カラム判定は、この回数が 0 より大きいかで置き換えられる
（`matched_fields` は回数から導出する）。

bm25 の生値は表示しない（事実5）。並び順を決めるためには使い続けるが、
`スコア: -0.00` が全件に並ぶ表示は「壊れている」としか読めない。

### 8. 色判定は共通ヘルパーへ寄せる（範囲は限定）

`--no-color` / `NO_COLOR` / 非TTY / 設定 の4条件判定は
`scripts/diff_viewer.py:174-179` と `utils/progress.py:34-39` に同型のものが既にある。
3つ目のコピーを作らず、`utils/terminal.py`（新設）に判定と ANSI 定数を置く。

移行の範囲は `diff_viewer.py` までとし、`progress.py` は触らない。
progress は判定に `progress.enabled` という別の設定キーを見ており、rich の使用可否という
別の関心事を持つため、無理に1本化すると条件が絡まる。

### 9. 例外は既存パターンに沿って追加

`LibrarySearchError` を親に、`QuerySyntaxError` を新設する。
`QueryTooShortError` は既存のまま残すが、メッセージに語の役割（検索語／除外語／限定語）を含める。

### 10. 対話メニューは現状のまま通る

`_menu_search()` の `answer.split()` → `" ".join()` 往復は、Python の `str.split()` が
全角スペース U+3000 も区切りとして扱うため、`関東　震災` が `関東 震災` に揃う（実測確認済み）。
`OR` / `NOT` / `原文:語` はいずれも空白で区切られた語として素通りする。ヘルプ文言だけ更新する。

## Risks / Trade-offs

- **本文に制御文字 `\x02` が含まれると強調がずれる** → OCR 出力（vision LLM のテキスト生成）に
  C0 制御文字が混入する見込みは実質ない。索引側でのサニタイズは `INDEX_SCHEMA_VERSION` の
  更新＝全件再構築を招くため今回は行わず、**マーカを対で解析する**（対にならない孤立マーカは
  強調として扱わず素の文字として落とす）ことで表示が壊れないようにする。
- **`OR` をモード切替にしたことで、混在した論理式が書けない** → Non-Goal として明示。
  必要になった時点で括弧付きパーサへ拡張できるよう、クエリ解析を独立した関数に切り出しておく。
- **`OR` / `NOT` を語として検索できない** → 対象が日本語の戦前公文書であり、実害はほぼない。
  将来クォートによるエスケープを足せる余地を残す。
- **抜粋 64 文字の上限** → 当初の16文字から4倍。これで足りない使い方が出たら Decision 5 の
  代替案（`highlight()` からの自前切り出し）へ移行する。仕様は「上限を持つ」としか書いていないため、
  上限を上げる変更は仕様の変更を伴わない。
- **JSON 出力の `snippet` から `[ ]` が消える（BREAKING）** → 現時点でこの JSON を機械処理して
  いる利用者はプロジェクト内に存在しない（`--format json` は CLI から人が叩く用途のみ）。
  README に変更点を明記する。
- **`OR` モードは結果が急増しうる** → `--limit` の既定20件と bm25 順で頭打ちになるが、
  「何件中の20件か」は現状も出していない。今回の範囲外とし、必要なら別途総件数の表示を検討する。

## Migration Plan

索引に触れないため、データ移行は不要。既存の `library/.index/search.db` はそのまま使える。

利用者側の互換性:

- 空白区切りの AND 検索は完全に従来どおり（Decision 2 の既定）
- 変わるのは抜粋の見え方（`[ ]` → 色）と JSON の `snippet` フィールド

ロールバックはコードの差し戻しのみで完結する。

## Open Questions

- `--snippet` の既定値を何文字にするか（16 のままか、40 前後へ引き上げるか）。
  実データが 0 件の状態では体感を測れないため、実装時に暫定値（40）を置き、
  実際の資料を索引したあとで `config.toml` から調整できる形にしておく。
  設定で変えられる以上、仕様にもタスク分解にも影響しない。
  → 実装では `search.snippet_chars = 40` を既定とした。`--snippet` と
  `config.toml` の両方から変えられる。

「設定」条件を見るための設定キーが検索側に無かったため `search.color`（既定 true）を
